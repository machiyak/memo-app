# Stored XSS の学習メモ

## 概要

メモ表示処理を例に、Stored XSSが発生する原因と対策を整理する。

Stored XSSは、ユーザーが入力したHTMLやJavaScriptがサーバー側に保存され、それが後からページに表示されたときにブラウザ上で実行される脆弱性である。

今回のメモアプリでは、ユーザーが投稿したメモ本文をSQLiteに保存し、一覧画面で表示している。
そのため、メモ本文の表示方法を誤ると、保存されたスクリプトが他のタイミングで実行される可能性がある。

---

## 脆弱な実装

脆弱な実装では、メモ本文を表示するときにJinja2の `safe` フィルタを使用している。

```html
<p>{{ memo["content"] | safe }}</p>
```

`safe` は、Jinja2 に対して「この文字列は安全なので、HTMLとしてそのまま出力してよい」と伝える指定である。

そのため、ユーザーが入力した文字列にHTMLタグやJavaScriptが含まれていた場合、それがブラウザで解釈される可能性がある。

---

## 問題点

問題は、信頼できないユーザー入力をHTMLとして出力していることである。

ユーザーが投稿するメモ本文は、アプリケーション側から見ると信頼できない入力であり、 `safe` を使うとテンプレートエンジンによる自動エスケープを回避してしまう。

例えば、メモ本文として次のような文字列が保存された場合を考える。

```html
<script>alert("XSS")</script>
```

脆弱な実装では、この文字列が単なるテキストではなく、HTML内のスクリプトとして解釈される可能性がある。

Stored XSSでは、攻撃用の文字列がDBなどに保存されるため、投稿時だけでなく、そのメモを表示するたびに影響が発生する点が問題である。

---

## 安全な実装

安全な実装では、`safe` を使わずにメモ本文を表示する。

```html
<p>{{ memo["content"] }}</p>
```

この場合、Jinja2 の自動エスケープにより、HTMLタグは実行されるコードではなく、文字列として扱われる。

例えば、次のような入力があっても、

```html
<script>alert("XSS")</script>
```

ブラウザ上ではスクリプトとして実行されず、概念的には次のようにエスケープされて表示される。

```html
&lt;script&gt;alert("XSS")&lt;/script&gt;
```

これにより、ユーザー入力がHTMLやJavaScriptとして実行されることを防げる。

---

## SQL Injection との違い

SQL Injection は、ユーザー入力がSQL文の構造に混入することで発生する。

一方、XSS は、ユーザー入力がHTMLやJavaScriptの構造に混入することで発生する。

整理すると次のようになる。

| 脆弱性           | 入力が混入する先          | 主な問題           |
| ------------- | ----------------- | -------------- |
| SQL Injection | SQL文              | 認証回避、意図しないDB操作 |
| XSS           | HTML / JavaScript | ブラウザ上でのスクリプト実行 |

どちらも共通しているのは、**ユーザー入力を命令や構造の一部として扱ってしまうこと**である。

そのため、ユーザー入力は原則として信頼せず、文脈に応じて適切に処理する必要がある。

---

## `safe` を使ってよい場合

`safe` は使ってはいけないわけではない。
例えば、アプリケーション側で生成した信頼できるHTMLを表示したい場合には使われることがある。

しかし、今回のようにユーザーが自由に入力できるメモ本文に対して `safe` を使うのは危険である。
